# Career

The player's progression in the first playable loop (GDR-0062, GDR-0063, ADR-0033): what a new game has, what
research unlocks, how a haul becomes research data, how voyages are launched, seeded and ended, when a fleet may
launch, and the save that holds it all. Written 13 Oct 2026 (track 7C).

This is its own document rather than a section of `content-model.md` because the career is not content: it is the
player's state and its rules, and the save is a storage format. The content it reads (families, research nodes,
starts, salvage blocks, `locked`) is described in `content-model.md`.

The model is pure, like `data::design::edit` for the drydock (ADR-0030): no Bevy, no I/O, wasm-safe, ordered containers
only. Every question takes the `Content` it should be answered against.

## The save (format 5)

`Career` holds **facts only**. Everything that can be derived from content is derived on demand and never stored,
so a content rebalance (a node's cost, a part's unlock) applies to a save as it is. The game stores
`Career::to_ron()` as a document in `saves/` (ADR-0031 adds the header line) and reads it back with
`Career::from_ron(text)` followed by `Career::reconcile(&content)`. `from_ron` takes a blueprint's input limits
(at most `limits::MAX_DOCUMENT_BYTES`, a leading byte order mark skipped).

|---|---|
| `packs` | the packs `(id, version)` it was last played with; informational (a note when one is missing at load) |
| `start` | the content start it began from |
| `seed` | the game seed (ADR-0024); voyage seeds come from it |
| `generator` | the voyage roller's version (`career::GENERATOR`, 2); see [Voyage roller versions](#voyage-roller-versions) |
| `researched` | research node ids, in the order researched |
| `data` | research data in store per family (f32, only amounts above 0) |

| `stock` | the workshop's parts by id (GDR-0108): what a fleet is fitted from; only counts above 0, never hull; left out when empty |
| `intake` | intact hauled parts waiting to be kept or dismantled (in the voyage's report since 18 Oct 2026, the rest kept when it is dismissed); left out when empty |
| `escorts` | saved design ids (`designs/`) flown as escorts; the flagship is the drydock's working design |
| `seen` | parts research unlocked that the player has since picked or selected in the drydock; left out when empty |
| `voyages` | per voyage ever launched: `launched` (count), `cleared` (the goal was cleared on a voyage that came home), `best_ticks` (the quickest such voyage, sim ticks at 30 per second) |
| `underway` | the voyage launched and not ended; left out when none |
| `log` | voyages launched, recalled, lost; items salvaged (parts and fragments unloaded) |
| `history` | the last voyages, oldest first, at most `MAX_HISTORY` (50; GDR-0091, home's LOG): per voyage `voyage` (a content voyage, or a cluster's name), `cluster` (the generated cluster it went to; left out for a content voyage), `outcome` (`Recalled`, `Cleared` or `Lost`), `ticks`, `report` (`parts` (intact) and `broken` and `fragments` by part id, `data`, `materials`, `logs`: data cores) and `new` (not shown in the LOG yet; left out when false); left out when empty. A voyage past 50 drops the oldest |
| `galaxy` | the galaxy and what the player knows of it ([below](#the-galaxy)); left out for content without a galaxy |

The text is written with the pack loader's options (`Some(..)` left out, four-space indent) and is deterministic;
unknown fields are errors, fields with defaults may be left out. `career::FORMAT` (5) is the format the game's
document header carries: raise it when a field is added or its meaning changes. There is no save compatibility before
release ([ADR-0044](adr/0044-no-save-compatibility-before-release.md), 18 Oct 2026): the game reads only this format,
and a save of an older one starts a new game in its place ([below](#where-the-game-keeps-the-save)). Unknown fields
are errors, so a field added without a new format would make an older build call a newer save damaged instead of
newer; with the format raised, its storage reports `Newer`. The history's reports are
what was credited, not derived. A save that cannot be read (newer, damaged, or from a newer voyage roller,
below) is never written over: the game keeps it as it is ("How the game uses it" below).

## Derived values

- **Unlocks** (`Career::unlocks(&content) -> Unlocks`): every part, material and frame that is not `locked` in the
  content, plus every `Part`, `Material` and `Frame` unlock of the researched nodes. `Unlocks::all(&content)` is
  everything (the development switch `?unlock=all`).
- **Mind capacity** (`mind_capacity`): the start's `mind_capacity` plus every `MindCapacity(n)` of the researched
  nodes (2, then 3 and 4 with the two mind expansions of the base pack).
- **Jump range** (`jump_range`, S; GDR-0093): the career's galaxy's `jump_range` plus every `JumpRange(s)` of the
  researched nodes (2.5, then 3.25 and 4 with the two jump calibrations of the base pack); 0 without a galaxy.
- **Open voyages** (`open_voyages`, `is_open`), in content order (the voyage map's): the start's `voyages`, and
  every voyage with `opens_after` whose voyages have all been cleared (`VoyageRecord::cleared`: a goal cleared on
  a voyage that came home). A voyage without `opens_after` opens only through a start. Loading drops records of
  voyages the content no longer has.
- **Part availability** ([GDR-0082](gdr/0082-drydock-layout-v2-and-part-availability.md)): the career fills no counts
  in the drydock's editing model since GDR-0108 (18 Oct 2026; until then every part was `Unlimited`): designs plan
  ahead, the workshop's `stock` limits the launch ([Voyage-readiness](#voyage-readiness)). The lab's runs may still
  set counts.
- **Fresh parts** (`fresh_parts(&content)`): `locked` parts a researched node unlocked that are not in `seen` (the
  drydock's NEW tags). `mark_seen(&content, part)` adds a fresh part to `seen` and says whether it was fresh (the
  game writes the save then); any other part changes nothing. `reconcile` drops seen ids the content no longer has,
  without a note (it is what the drydock showed, not progress).

## Research

`can_pay(&content, node)` answers whether a node can be researched now; `research(&content, node)` does it and
returns the node. Refusals (`career::Refusal`), checked in this order: `UnknownNode`, `AlreadyResearched`,
`Requires(missing)` (the node's `requires` not yet researched, in its order), `CannotPay(shortfalls)` (every data
cost, then every material cost, that the stores can't meet, with what is held and what it costs). A refused call
changes nothing.

Paying takes each cost from its store at once and unlocks immediately (GDR-0063). Research data within
`DATA_EPSILON` (0.001) of a cost counts as enough, so a sum of tenths that lands a hair below its cost still pays; a
store paid down to that little is removed. Stores hold only amounts above 0.

## Unloading a haul

A `Haul` is the items a voyage brought home with counts (`BTreeMap<HaulItem, u32>`). `HaulItem` mirrors the sim's
cargo item (`Part { part, material }`, `Broken { part, material }`, `Fragment { part }`, `DataCore`); `data` does not
depend on `sim`, so the game converts. `career::unload(&content, &haul) -> HaulReport` is pure and gives (GDR-0108;
`share` is the workshop's `broken` rule, 0.25):

| Item | Gives |
|---|---|
| an intact non-hull part | nothing yet: it goes to the workshop's `intake` (`Career::recalled`), to be kept or dismantled |
| a broken non-hull part | its `salvage` block's `data` for its family, and `share` × its recipe's materials, per item |
| a hull part, whole or broken | its armour material's `salvage.data` × the part's area (slopes count half a cell) for that family, and `share` × area units of the armour material, per item |
| a fragment | the `fragment` materials of the part that left it; no data |
| a data core (`DataCore { trail, signal }`) | one log in `logs`; which signal it decodes into the career keeps ([The galaxy](#the-galaxy)) |
| an unknown part, a hull part without (or with an unknown or non-armour) material, a part without a block | nothing (parts are still listed) |

The shares are summed per material over the whole haul and rounded to the nearest unit once. A non-hull part item
that carries a material gives its own block; the material is ignored. Counts saturate; sums are bounded by
`MAX_DATA` and `MAX_MATERIALS`. The report lists `parts` (intact), `broken` and `fragments` by part id, `data` per
family and `materials`; `items()` counts every kind.

## The workshop

GDR-0108 (18 Oct 2026), `career/workshop.rs`. The content's workshop is the first facility with `workshop` rules
(`Content::workshop`: `dismantle` 0.4, `broken` 0.25, `keep` 2, placeholders).

- **Stock**: `stock()`, the parts a fleet is fitted from. A new game has its start ship's non-hull parts
  (`Content::ship_parts`) and the start's `materials`. Fitting takes nothing: the stock grows by keeping and
  fabricating and shrinks only by dismantling stock.
- **Sorting the intake**: `keep(part, n)` moves `n` into stock; `dismantle(&content, part, n)` gives the part's data
  and `dismantle` × its recipe (rounded to the nearest unit over the `n`; `dismantle_yield` is the same, pure) and
  returns it; both refuse with `NotInIntake` for more than wait. `suggested(&content, &need)` per intake part: keep
  until the stock holds the rules' `keep` or what `need` (the fleet's parts, `fleet_parts`) asks for, dismantle the
  rest; `sort_suggested` does it for every part and returns what the dismantled ones gave. `keep_intake` keeps the
  whole intake and returns how many (18 Oct 2026: the voyage's report sorts the intake, and the game keeps what it
  leaves when it is dismissed, or at home without an open report).
- **Fabricating**: `can_fabricate(&content, part, n)` / `fabricate`: refused in this order with `UnknownPart`,
  `LockedPart` (not unlocked), `NoRecipe` (salvage only), `NeedsFacility(upgrade)` (the recipe's `needs` not open),
  `CannotPay(shortfalls)` (every material short, in id order); else the recipe × `n` leaves the store and `n` go into
  stock. `fabricable(&content, part)`: the most it can make now (0 when one is refused, else what the scarcest
  material pays for).
- **Dismantling stock** (18 Oct 2026, later): `dismantle_stock(&content, part, n, &need)` gives `dismantle` × the
  recipe like an intact hauled part but **no research data** (the stock is the workshop's own: nothing new to study,
  and fabricating then dismantling would otherwise turn materials into data) and returns it. Refused with `NoRecipe`
  (it would give nothing), `NotInStock` (more than the stock holds, or none), and `FleetNeeds { part, need, stock }`
  when the stock would fall below what the fleet carries (`need`, as for `suggested`): refused rather than warned,
  since a fleet short of a part cannot launch. `spare(part, &need)`: the stock beyond the fleet's need, the most it
  allows.

## Voyages

- **Launch** (`voyage_launched(&content, id) -> seed`): refused while another voyage is underway (`Underway`) and
  for a voyage that is not open (`NotOpen`). It returns the seed the sim rolls this launch from, adds one to the
  voyage's `launched` and the log, and marks the voyage underway. The game writes the save now, so closing the game
  mid-voyage counts as losing it (GDR-0062; see loading below).
- **Seed** (`voyage_seed(id)`, the next launch's): `splitmix64(seed ^ splitmix64(fnv1a64(id) ^ launched))`, with
  64-bit FNV-1a over the id's UTF-8 bytes (never Rust's `DefaultHasher`) and one step of SplitMix64 (it adds the
  generator's increment, then mixes), both defined once in `data::hash` for the career and the sim's RNG streams and
  pinned by tests. The same save rolls the same voyage; each launch rolls a new one. It is part of the save format:
  changing it needs a new `GENERATOR`. Fixed values are tested (`tests/career.rs` `voyage_seeds_are_fixed`):
  seed 4207, `yard_approach`, no launches → 9993844787240758234; after one launch → 8810720374438629928.
- **End** (`voyage_ended(&content, id, end)`, refused with `NotUnderway` for any voyage but the one underway):
  - `VoyageEnd::Recalled { haul, cleared, ticks }`: the haul is unloaded into the stores; `cleared` marks the voyage
    cleared and keeps the quickest `ticks` as `best_ticks`; outcome `Cleared` or `Recalled`; the log counts a
    recall and the items.
  - `VoyageEnd::Lost { ticks }`: the haul stays behind (there is none to pass), the goal does not count; outcome
    `Lost`.
  - Either way the voyage's result joins the history, new, and is returned (`last_voyage()`). Cleared voyages stay
    launchable for more haul.
- **The LOG** (GDR-0091): `history()`, `unread()` (results not shown yet: the mast glows) and `read_log()` (all shown;
  true when one was not, then the game writes the save).

## The galaxy

Galaxy track E4, 16 Oct 2026 (GDR-0093, [GDR-0096](gdr/0096-career-galaxy-format-3.md)): `Career::exploration()`
(`data::career::Exploration`, `crates/core/data/src/career/galaxy.rs`; tests `tests/career_galaxy.rs` on a small
hand-made skeleton, and the `galaxy` crate's `tests/career.rs` for a new game's generated galaxy).

| Field | Meaning |
|---|---|
| `skeleton` | the galaxy as generated for this game (`data::skeleton::Skeleton`, ADR-0035): never regenerated on load; about 65 KB of the save's RON. Since generator version 2 (E7) its `pieces`: the set pieces, voyage id → cluster id |
| `charted` | charted clusters by id: home from the start, every cluster a voyage was launched into (arriving charts it, lost or not); per cluster `launched` (left out when 0) |
| `signals` | the signals heard, in the order heard: `lead` (`Trail((trail, signal))`, skeleton indices, or `Voyage(id)`: a slice voyage), `cluster` (where it leads), `area` (`(centre, radius)` in S/100 now), `state` (`Fresh`, `Narrowed`, `Located`, `Done`) |
| `logs` | data cores brought home and not decoded yet, as `(trail, signal)` |
| `gates` | gate clusters opened (a guardian beaten) |
| `pins` | the content's voyages on clusters (voyage id → cluster id): the skeleton's set pieces |
| `memories` | the memory log: lore fragments (ids) found at the ends of their trails, in the order found (left out when empty) |
| `underway` | the cluster a voyage was launched into and has not ended (left out when none) |

- **New game**: `Career::begin_galaxy(&content, skeleton)` with the skeleton of the content's first galaxy, generated
  from the game seed by the game (`galaxy::generate`; `data` does not depend on the generator): home is charted, the
  slice lies on its set pieces. A career with a galaxy keeps it.
- **Jumps** (`jump_from(cluster)`): from home or any charted cluster within the jump range (integer distances in
  S/100), the nearest one (the lowest id on a tie), not the cluster itself while another reaches it; `None` beyond them
  all. `band_open(band)`: jumps reach the galaxy's first band and each band past it once a gate of the band outside it
  is open. `warp_seconds(k)`: the galaxy's `warp`, 3 s + 2 s per S from `jump_from` (GDR-0093). `blind_target(spot)`:
  where a blind jump to a spot goes, the cluster nearest it that a jump reaches, within 1.5 of the galaxy's spacings
  (`BLIND_REACH`), neither home nor a slice voyage's (GDR-0097).
- **Cluster voyages**: `cluster_seed(k)` is `splitmix64(seed ^ splitmix64(cluster seed ^ launched))`;
  `cluster_launched(&content, k)` (refused `Underway` while a voyage or cluster voyage is underway, `NoGalaxy`,
  `UnknownCluster`, `OutOfReach`, `BandClosed`) charts it, counts the launch and marks it underway; `cluster_ended(&content, k, end)`
  ends it like `voyage_ended` (recalled: unloaded, every data core of the haul a log unless its signal is heard or
  logged already; lost: the haul, cores included, stays behind) and adds a history entry with the cluster's name and id.
  The voyage map launches them after their warp (E6, GDR-0097); `?scene=voyage&cluster=` flies one as a practice run.
- **What a launch carries** (`leads(&content, k) -> Leads`, for `sim::VoyagePlan::roll_interior`): the trail places in
  the cluster that a heard signal not done leads to (signals' sites: hidden until close, bearings from a scan), and the
  log places (a source of form `Log`) whose core is neither decoded, logged nor heard (their site's first wreck holds
  it).
- **Signals**: `hear(signal)` adds a trail's signal fresh with the skeleton's area (once); `decode(k)` decodes log `k`
  into its signal (free, GDR-0080); `narrow(&content, signal, from)` is a scan's bearing heard in cluster `from`: in the
  signal's own cluster it is located; elsewhere the radius shrinks to the galaxy's `signal_area.narrow` (60 %, at
  least 1; it halved until 17 Oct 2026, GDR-0098) and the centre moves towards the place until the place lies within
  `signal_area.offset` (60 %) of the new radius, and once no other cluster lies inside the signal is located (its area
  the cluster's place, radius 0). `scanned(&content, k, skip)` is a scan taken in cluster `k`: every heard signal not located yet
  that leads there or whose area holds the cluster narrows from it, except those in `skip` (the game passes those
  narrowed on this voyage already). `beacon(&content, place)`: a scan swept over a trail place whose signal's source is
  a `Beacon`: heard. `found(&content, signal, done)`: its site was seen (found) or cleared, or seen with nothing to
  clear (done); the area becomes the cluster's place. States only move forward (fresh, narrowed, located, found, done); the game
  gives a voyage's finds to the career at its end, lost or not (GDR-0097).
- **Rewards** (E8, [GDR-0098](gdr/0098-slice-in-the-galaxy-and-rim-rewards.md)): the last signal of a trail done gives
  the trail's reward, once: its end a gate, the gate opens; a lore trail's fragment joins `memories`; the trail
  template's `gives` (a cache's research data and materials) goes into store. A find, so kept on a lost voyage.
- **Gates**: `open_gate(k)` records a gate of the skeleton as opened; a trail's guardian beaten and the Warden cleared
  open theirs.
- **The slice** (E7, GDR-0098; E4 pinned it in a chain, GDR-0096): every voyage of the content lies on the cluster the
  skeleton's set pieces put it on; a launched voyage charts its cluster, an
  open one not cleared is a located `Voyage` signal, a cleared one's signal is done, and a cleared one on a gate (the
  Warden's) opens it: the slice is the rim's first gate trail. Kept in step at every launch and end of a voyage and at
  load. Slice voyages keep their own records and seeds and launch from the voyage map as before; the jump range does
  not gate them.
- **Loading** (`reconcile`): pins and `Voyage` signals of voyages the content no longer has go; signals and logs the
  skeleton doesn't have go (a note); memories of fragments the content lost go; a cluster still underway ends as lost
  (a note); the slice is brought in step.

## Voyage-readiness

`career::voyage_ready(&content, &unlocks, mind_capacity, stock, &flagship, &escorts) -> Vec<Readiness>` (`stock`:
`Some(&career.stock())`, or `None` for unlimited, the free mode); empty means
ready. Entries, in this order: per ship (flagship first, then escorts by index, `FleetSlot`)

1. `LockedFrame { ship, size, frame }`: the blueprint's `size` (a drydock design's frame) fits no unlocked frame;
   `frame` names the first frame in content order it would fit (a locked one), if any. Same rule as a start's ship.
2. `LockedPart { ship, part }`, then `LockedMaterial { ship, material }`: each locked (or unknown) part and material
   it uses, once, in placement order.

then for the fleet

3. `MissingParts { part, need, have }` (GDR-0108): per unlocked part the fleet carries more of (all ships together)
   than the stock holds, in id order.
4. `TooManyCores { cores, capacity }`: its logic cores (all ships) exceed the mind capacity.
5. `NoCargo`: no ship has a hold (`Content::ship_hold`: cargo on its main piece, as the sim counts it; cargo on a
   piece that falls off at spawn holds nothing), so nothing salvaged can come home. A warning only:
   `Readiness::blocks()` is false for it alone.

The drydock and the map show the first entry. Flight-readiness (power, thrust: the design report) is the sim's
question and is checked by the game next to this list.

## Loading a save against changed content

Content may change between versions (a rebalance, a removed mod). `Career::reconcile(&content) -> Vec<Problem>`
runs after every load and never fails or panics; each change comes back as a warning (with kind, id and a field
path such as `researched[1]` or `data.lasers`) for the status line:

- a pack of `packs` that is not loaded now is noted; `packs` becomes the current list;
- an unknown `start` is replaced by the content's first start;
- researched nodes the content doesn't have, or listed twice, are dropped (their unlocks go with them);
- data of unknown families and materials the content doesn't have are dropped, in the stores and in the history's
  reports (`history[3].report.data.lasers`); data that is not finite or below 0 is dropped; amounts above `MAX_DATA` or `MAX_MATERIALS` are lowered to
  it; zero amounts are dropped silently;
- records of voyages the content doesn't know are dropped, and so are the history's entries of them (`history[k]`);
  a history longer than `MAX_HISTORY` (written by hand) loses its oldest;
- a voyage still `underway` was interrupted: it ends as `Lost` (ticks 0) when its launch is on record, else the
  mark is dropped.

The queries themselves cope with content that was not reconciled (an unknown start gives mind capacity 0 plus
research and opens only the voyages whose `opens_after` are all cleared; unknown nodes unlock nothing; research data
that is not finite counts as none, so it never pays).

### Voyage roller versions

`generator` names the voyage roller a career's voyages roll with (ADR-0024): the voyage seed and the sim's
`VoyagePlan::roll` (`docs/sim.md` "Rolling a plan").

| Version | What changed |
|---|---|
| 1 | 13 Oct 2026 (track 7E): the plan drew on a generator seeded like the sim's encounter stream; wrecks rolled their missing parts on that stream when they spawned, so a wreck depended on the order the sites were reached |
| 2 | 13 Oct 2026 (review): the plan's generator is salted (`sim::voyage::PLAN_STREAM`), and each wreck carries its own damage seed in the plan |

Only the current version is read (ADR-0044): `Career::from_ron` refuses a save of another `generator` (an error on
`generator`), never resets it, since this build would roll its voyages differently. Nothing a save stores refers to
a rolled voyage (no mid-voyage saves, GDR-0062), so a new version needs no more than raising `GENERATOR` and
`career::FORMAT` together.

## Where the game keeps the save

Track 7F, 13 Oct 2026: `game::career` (`crates/client/world/src/career.rs`; tests there, `cargo test -p game career`).

- **The document**: `saves/<slot>` in the player storage (ADR-0031: on the web the browser's IndexedDB since 16 Oct
  2026, ADR-0041, key `saves/career` in the database `space-game`, read into memory before the game starts and
  written behind it; `<data dir>/saves/career.ron` on desktop; memory where the platform has none, with a
  note). The text is `Career::to_ron()` after the storage's header line `// space-game: saves, format 5, saved
  <unix seconds>` (`CareerDoc`, format `career::FORMAT`, the oldest it reads too). The slot is `career`; `?save=<slot>` plays another one
  (a storage name: `a-z 0-9 _ -`; another name falls back to `career` with a note).
- **Loading** (`career::load`, in the plugin's build before the first frame): read → `Career::from_ron` →
  `reconcile` (the first change and how many more become a note on home) → a career without a galaxy gets the
  content's first one (`career::chart`: `galaxy::generate` from the game seed, `begin_galaxy`; content without a
  galaxy leaves it without, one that doesn't generate says NO GALAXY). No save, a save of an older format (the
  storage's `Older`: a log line and the note A NEW GAME, ADR-0044), or `?newgame=1`: a new game from
  the content's first start, seeded with the clock (Unix seconds), written at once; the drydock then docks a copy
  of the start's ship (`rim_skiff`), saving the last design's unsaved changes first so BLUEPRINTS keeps them.
- **A save that doesn't read** (broken RON, unknown fields, a header from a newer build, a newer voyage roller) is
  **kept as it is**: the
  game runs a new career in memory as a stand-in, never writes it, keeps the drydock's design and says so on home
  ("THE SAVE IS KEPT AS IT IS"). `?newgame=1` starts over in its place. Content without any start gets the same
  treatment (a stand-in career that unlocks what the content doesn't lock, mind capacity 0).
- **Writes**: at a new game, after every FLEET change, when the drydock first shows a fresh part (`seen`); the
  research screen (7G) writes after UNLOCK and the voyage (7H) at launch and end. Never during a voyage. A failed
  write leaves the change in the running game and says why (home's notes, FLEET's status line).
- **Voyages** (track 7H, `client.md` "Voyages"): a launch needs a voyage-ready fleet by what the career grants. The
  development launch `?scene=voyage&voyage=<id>` flies what the career would refuse (a voyage not open, a fleet that
  isn't ready by the career's own unlocks, so also a fleet only `?unlock=all` allows) as a practice run: rolled
  from `voyage_seed` (the seed the next launch would get), never recorded or written.
- **`?unlock=all`** (free mode): the drydock offers every part, material and frame (`Unlocks::all`), shows nothing
  locked and no NEW tags, and checks voyage-readiness against everything. No unlock is ever written: the save keeps
  the career's own progress (FLEET still saves its escorts).
- **Escorts**: their saved designs are read at start and whenever home or the drydock opens (`EscortDesigns`); an
  escort whose design is gone or doesn't read leaves the fleet, the save is written and home notes it.

## How the game uses it

- **Start**: read `saves/career` → `Career::from_ron` → `reconcile` (show the notes); none: `Career::new(&content,
  start, seed)` with the content's first start.
- **Drydock**: `unlocks` gates the palette, armour and frames (locked ones shown dimmed if research unlocks them,
  else hidden; locked frames dimmed; `docs/drydock.md`); `available` gives each
  palette row's count (`∞` today) and reaches the editing model (`Granted::counts` → `PlayerDesign::set_available` →
  `data::design::edit::Drydock::set_available`), which refuses a placement with none left; `fresh_parts` gives the NEW tags
  and `mark_seen` ends them; `voyage_ready` gives the status line's voyage-ready line.
- **FLEET**: `escorts` and `set_escorts`; `mind_capacity` limits the picks; `voyage_ready` for the fleet.
- **Research screen**: `data()` and `materials()` on top, `can_pay` per node (the refusal says why not),
  `research` on UNLOCK, then write the save; a `JumpRange` node shows the jump range before and after
  (`jump_range`).
- **Map**: `open_voyages`, `voyage(id)` for cleared and best time, `voyage_ready` for SET COURSE.
- **Launch**: `voyage_launched` → write the save → roll the voyage with the returned seed and `mind_capacity`.
- **End**: convert the surviving vessels' cargo to a `Haul` (`game::voyage::fleet_haul`), `voyage_ended`, write the
  save, show the debrief (built from the voyage's result, the career before and after, and the flight's kills and losses,
  which the model doesn't keep).
